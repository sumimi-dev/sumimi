How much traffic can a 1 vCPU box take?

The short answer is a rule with two numbers in it. The long answer is how the rule was measured, what it does not cover, and the two traps that had to be removed from the measurement before it could be believed.

The question

Sumimi promises to stay inside 256 MB on a 512 MB box and 512 MB on a 1 GB box. A promise like that is only useful if you can turn it into a number of visitors. So: how many requests a second can a one-core VPS take before the promise breaks?

The answer has to be a measurement, because the memory a request costs is not a property of the request. It is a property of the churn — how fast the allocator is asked for memory, and how much of what it asked for it kept.

The instrument

The load generator and the probe live in a separate repository, sumimi-gotest, written in Go with the standard library only, so it runs on a machine that has nothing on it but the server. It is a second implementation of the API on purpose: a probe that shares code with the server cannot disagree with it, and a probe that cannot disagree cannot find anything.

Two rules made the numbers comparable:

  • The server reports its own peak. The exact high-water mark comes from /proc/self/status (VmHWM) — the process's own number, not the parent's guess about it. The report says which machine was measured, so a number without a machine is not a number.
  • The worst of three runs is the number. The promise is about the peak, so the peak is what the table carries — not the average, and not the best run.

The rule

The first machine gave a clean line: the peak ≈ 68 MB + 7.8 MB per 1 000 requests a second. The engine was only 2–12 MB of it. The rest was the collection path and the allocator.

One machine is an observation, not a law — two points cannot prove a rule, and the two might be a coincidence. So we measured it on three machines with three different CPUs:

Three machines, three CPUs, and at the same rate they cost the same memory. So a stronger CPU does not mean less memory — it means the same memory reaches a higher rate. The CPU decides how far up the rate axis you can go; the memory follows from where you go.

The network is not free

Every number above was loopback traffic. The controlled re-measurement — the same container, the same server, the same rate, the server restarted every time, the generator inside the container and then out on the laptop over the public internet (39 ms of round trip):

the trafficthe three peaksthe worst
loopback (the generator inside)215 / 207 / 206 MB215 MB
the public internet (the generator outside)261 / 251 / 244 MB261 MB

The network costs about 20% of the memory. The requests arrive in batches — they wait for each other on the wire — so the server parses a batch at a time and the peak is higher. The tail follows: at 5 000/s over the internet 0.7% of the requests timed out (529 of 75 000), against zero over loopback.

This is why the default rates are 15 000/s on the minimum tier and 30 000/s on the recommended one: the memory numbers were taken over loopback, so they carry no margin, and the network takes about a fifth of it.

The gate: refusing is a feature

The server admits a fixed rate and turns the rest away with a 503 and a Retry-After. Measured in a container, with the released binary and the minimum tier's 128 MB engine:

Offering 30 000/s to a server limited to 20 000/s produces 180 313 refusals — and the memory does not grow. The box is protected. The same thing happens past a machine's ceiling: the EPYC served 16 700/s and refused the rest, and its memory stopped growing at 236 MB rather than climbing.

Two traps

Both of these produced numbers that were wrong, and both had to be found before the rule could be believed.

The container that thought it had 7.7 GB

The server sizes itself from the memory it can see. In a container it read /proc/meminfo — which is the host's memory, not the container's. A container limited to 512 MB believed it had 7.7 GB, sized the engine at 256 MB, set the gate at 40 000/s, and got OOM-killed. Fixed in v0.4.1: the cgroup limit is read too, and the smaller of the two wins.

The peak that was not the server's

ru_maxrss on Linux is not the child's peak: Linux does not reset it on exec, so a child's high-water mark still carries the parent's resident set from the moment of the fork. The load generator was a big process by the third measurement, so its memory was reported as the server's. The same rate measured 418 MB and then 831 MB — while the server's own VmHWM sat at 130–140 MB the whole time.

The rule that came out of it: the server reports its own peak, in /api/heartbeat, and that is the number to believe. ru_maxrss is only the fallback for the platforms with no /proc.

So: how much traffic?

Here is the whole thing, with the caveats attached:

  • A 512 MB / 1 vCPU box holds 20 000 requests a second on memory alone — measured, 208 MB peak in a container. Over a real network, run it at 15 000/s.
  • A 1 GB / 1 vCPU box has twice the budget, so the ceiling doubles to 40 000/s and the safe number over a real network is 30 000/s.
  • The core is the limit before the memory is. Our slowest box (two slow EPYC cores) topped out at ~16 700/s and refused everything above it; the fastest (a 10-core M5) reached 113 000/s. A single core lands in between — expect somewhere around 8 000–20 000 requests a second — and the gate has to be set below the machine's ceiling, not above it.
  • The disk fills first. 15 000 page views a second is 1.3 million a day, which is about 50 GB a year of rows. Keep the history you want, let the retention window and sumimi prune do the rest, and keep a backup.

The full method, the four limits and the tables are in the memory and capacity reference; the design behind them is in MEMORY.md in the repository.

The measurement reports themselves are published, as they were taken, in the repository's benchmarks/ directory — including the ones that did not come out the way we expected. Or start with why this exists.
