Install

From an empty machine to a running analytics server in about five minutes. You need a 64-bit Linux box (or macOS), some disk for the programs and the database, and nothing else — no database server, no container runtime, no Node, no shared library to install.

1. Get the release archive

Every release publishes an archive containing:

FileWhat it is
sumimiThe one executable: the analytics server (collection API, statistics API, authentication, the dashboard shell and the tracker) and the analysis CLI. A self-contained executable — DuckDB is compiled into it. sumimi serve … runs the server, every other subcommand is the analyser.
sumimi-server
sumimi-client		Symlinks to sumimi, for people who prefer the explicit name. The program decides its mode by the name it was invoked under, so sumimi-server serve and sumimi-client summary both work. There is nothing extra to download.
js/The dashboard frontend files (sumimi-app.js, sumimi.css) and a copy of the tracker. The frontend is served from a CDN by default, and from here when you set SUMIMI_APP_URL=/app; the tracker itself is compiled into the server binary and always served by the backend.
docs/This documentation site, served by the server at /docs.

DuckDB is linked statically: its engine is compiled into the executable. It is self-contained — there is no libduckdb.so to ship, no LD_LIBRARY_PATH to set, no rpath to fix and no ldconfig step. Copy one file and run it.

One binary, two modes

There is nothing to choose: you download one file, and the subcommand decides what it does.

I want to…Command
Run the server (collect page views, serve the dashboard)sumimi serve --db … --port 3000
Create or reset the admin accountsumimi admin --username admin
Print the resolved configurationsumimi config
Analyse the data from the command linesumimi summary <website-id>, sumimi pages, sumimi export, …
Fill a database with demo trafficsumimi seed --db ./sumimi/data.duckdb

If you prefer the explicit names, the symlinks sumimi-server and sumimi-client are in the archive: sumimi-server serve is the server and sumimi-client summary is the analyser. They are the same file.

Want a smaller binary instead?

There is an optional dynamic build: make build-small links the prebuilt DuckDB library instead of compiling it in, which gives you a noticeably smaller executable — at the price of one extra file to ship. In that case libduckdb.so (or libduckdb.dylib on macOS) has to sit next to the binary, and the loader has to be told where to find it. The default release is static, so this only matters if you build from source.

Linux (x86-64)

curl -fsSL https://github.com/sumimi-dev/sumimi/releases/latest/download/sumimi-linux-amd64.tar.gz | tar xz
ls -l

You should now see sumimi, the sumimi-server and sumimi-client symlinks, js/ and docs/.

macOS (Apple silicon)

curl -fsSL https://github.com/sumimi-dev/sumimi/releases/latest/download/sumimi-macos-arm64.tar.gz | tar xz

The same layout, and the same rule: the executables are self-contained on macOS too, so there is nothing to copy next to them.

Windows

curl -fsSL https://github.com/sumimi-dev/sumimi/releases/latest/download/sumimi-windows-amd64.zip -o sumimi.zip
Expand-Archive sumimi.zip

Build from source

If you would rather compile it — to match an unusual architecture, for example — you need a Rust toolchain. The first build compiles DuckDB from source and takes a while; afterwards it is quick. 

git clone https://github.com/sumimi-dev/sumimi.git
cd sumimi
cargo build --release
# the executable lands in target/release/sumimi

cargo build --release produces the same self-contained executable as the release archive. make build-small produces the smaller dynamic build described above, and copies libduckdb.so into target/release/ for you.

2. Install the executable

# the one executable: the server and the analysis CLI
sudo install -m 0755 sumimi /usr/local/bin/

# optional: the explicit-name symlinks, if you prefer them
sudo ln -sf /usr/local/bin/sumimi /usr/local/bin/sumimi-server
sudo ln -sf /usr/local/bin/sumimi /usr/local/bin/sumimi-client

# optional: the js/ and docs/ directories, for the dashboard frontend
# served by the backend itself and for the docs site at /docs
sudo install -d -m 0755 /opt/sumimi
sudo cp -r js docs /opt/sumimi/

That is the whole installation. The binary carries DuckDB inside it, so there is no library to install alongside and no loader configuration to do. If you would rather keep everything together in one directory, install it into /opt/sumimi and point the service's ExecStart at that path.

The js/ and docs/ directories are optional. You need js/ only if you serve the dashboard frontend from the backend yourself (SUMIMI_APP_URL=/app); by default it comes from a CDN. docs/ is this documentation site, served at /docs. The tracker at /sumimi.js is compiled into the server binary, so it is available either way.

3. Create the admin account

The server has one user: the administrator. Create it before the first run so the password is one you chose. 

sumimi admin --dir /var/lib/sumimi \
  --username admin --password 'a-long-passphrase'

If you leave --password out, a strong password is generated and printed once: 

$ sumimi admin --dir ./sumimi --username admin
admin user 'admin' ready
password: 8f3c1b9d0e7a4f26b5c8d1e3a9f7b2c4
(store it now — it is not shown again)

If you skip this

The first serve on an empty database creates the admin user anyway, using SUMIMI_ADMIN_USER (default admin) and SUMIMI_ADMIN_PASSWORD. If the password is unset, one is generated and printed to the service log exactly once. It is never stored in plaintext.

4. Run the server

sumimi serve --dir /var/lib/sumimi --host 127.0.0.1 --port 3999

An instance is a directory. Everything it owns lives inside it, so backing it up, moving it and deleting it are one operation on one path: 

/var/lib/sumimi/
├── data.duckdb      the events
├── instance.sqlite  the accounts, the log, the imports, the cache
├── logs/            the server's log files
├── acme/            the TLS certificate cache
└── jwt-secret       the signing secret

To serve HTTPS directly — without a reverse proxy in front — add --ssl: 

sumimi serve --dir /var/lib/sumimi \
  --ssl example.com --ssl-email you@example.com

--ssl-domain is still accepted as an alias for --ssl.

The flags you will use most:

FlagEnvironment variableDefaultMeaning
--dir <path>SUMIMI_DIRsumimiThe instance directory: the events, the accounts, the log, the imports and the cache all live inside it.
--db <path>SUMIMI_DB<dir>/data.duckdbPath of the data file — for keeping the events on a bigger disk than the rest.
--backend <name>SUMIMI_BACKENDduckdbThe data engine: duckdb or sqlite. Both store the same tables and answer the same reports; DuckDB is smaller and faster on the heavy aggregations, SQLite is an ordinary file that many readers can open at once.
--host <addr>SUMIMI_HOST0.0.0.0Address to bind to.
--port <port>SUMIMI_PORT3000Port to listen on.
--jwt-secret <secret>SUMIMI_JWT_SECRETgeneratedSecret used to sign tokens. A random one is generated and stored in the instance directory on first run if unset.
--retention-days <n>SUMIMI_RETENTION_DAYS0Default retention window in days. 0 means keep forever.
--country-header <name>SUMIMI_COUNTRY_HEADERnoneHeader carrying the country code, e.g. CF-IPCountry.
--js-dir <path>SUMIMI_JS_DIRjsDirectory holding the dashboard frontend files. Only used when SUMIMI_APP_URL=/app makes the backend serve the frontend itself.
--docs-dir <path>SUMIMI_DOCS_DIRdocsDirectory holding the documentation site served at /docs.
--ssl <domain>SUMIMI_SSL_DOMAINnoneServe HTTPS with a certificate obtained and renewed automatically over ACME. --ssl-domain is accepted as an alias. See Let Sumimi manage TLS itself.
--ssl-email <address>SUMIMI_SSL_EMAILnoneContact address registered with the ACME provider. Let's Encrypt sends expiry notices there.
--ssl-cache-dir <path>SUMIMI_SSL_CACHE_DIR<instance directory>/acmeDirectory holding the ACME account and the certificates. Back it up.
--ssl-port <port>SUMIMI_SSL_PORT443Port used for HTTPS when --ssl is set.

Two more settings have no flag — they are environment-only because they are per-site policy rather than per-server:

  • SUMIMI_KEEP_QUERY — whether to store the query string of the collected URLs. It is on by default, because that is what Umami stores and the marketing parameters (UTM, ad click ids) live in it — they are parsed out of it either way. Set it to 0 to keep the parameters but drop the raw query string, which is where session tokens and other personal data tend to be.
  • SUMIMI_STORE_TITLES — whether to store the page title. It is on by default (Umami stores it); set it to 0 to save the space — the title is roughly half of the stored bytes and almost nobody looks at it.
  • SUMIMI_STORE_FULL_REFERRER — whether to store the referring URL in full. It is on by default; set it to 0 to keep the host alone, which is what the referrer breakdown groups by anyway.
  • SUMIMI_APP_URL — base URL of the dashboard frontend (sumimi-app.js and sumimi.css). It defaults to https://cdn.jsdelivr.net/gh/sumimi-dev/sumimi@main/js, so the frontend is served from a CDN out of the box and the backend only ships a tiny HTML shell. Set it to /app to serve the frontend from the backend's own js/ directory instead — that is what you want on an air-gapped machine. The tracker (sumimi.js) is served by the backend itself and is unaffected by this setting.

A few more environment variables tune the process rather than the data:

  • SUMIMI_DUCKDB_MEMORY_LIMIT (default min(256MB, RAM / 4)) — DuckDB's memory limit, in bytes. A 512 MB box gets 128 MB, a 1 GB box gets 256 MB, and nothing gets more than 256 MB. It is a ceiling, not an allocation: the whole process stays under 256 MB on the smallest supported machine, and under 512 MB on a 1 GB one — both are asserted on every CI run.
  • SUMIMI_MAX_QUEUE (default 100000) — how many events may be buffered in memory before the oldest are dropped.
  • SUMIMI_FLUSH_INTERVAL_SECS (default 2) — how often the writer commits a batch to disk.

  • The settings were called SUMAMI_* until v0.2.0. The old names still work — they are in people's .env files and systemd units — but the new names win when both are set. Rename them the next time you touch the file.

  • SUMIMI_UPTIME_INTERVAL_SECS (default 300) — how often the uptime of the websites is checked. 0 turns the checker off.
  • SUMIMI_UPTIME_TIMEOUT_SECS (default 10) — how long a website has to answer before it counts as down.
  • SUMIMI_CACHE_STALE_SECS (default 30) — how old a cached report may be. The writer commits every couple of seconds, so a cache that only accepted the current version of the data would never hit on a busy site; with the window, the numbers on the screen are at most that old and the query runs once instead of a hundred times. 0 means "only while the data has not changed".
  • SUMIMI_JWT_SECRET_FILE — path of a file holding the token secret, if you would rather keep it out of the environment.

The admin subcommand has its own flags — --username (SUMIMI_ADMIN_USER, default admin), --password (SUMIMI_ADMIN_PASSWORD) and --db (SUMIMI_DB). A third subcommand, config, prints the resolved configuration and exits.

HTTPS without a reverse proxy

With --ssl example.com the server obtains a Let's Encrypt certificate on its own over ACME and renews it in the background. There is no certbot and no cron job, and no reverse proxy is needed just to serve TLS. The challenge used is TLS-ALPN-01, so port 443 has to reach the Sumimi process directly — behind a proxy that terminates TLS, use the proxy's own ACME support instead.

5. Create a website

Log in and create the website you want to measure. The website id is what the tracker needs. 

# log in
curl -s -X POST http://127.0.0.1:3999/api/login \
  -H 'content-type: application/json' \
  -d '{"username":"admin","password":"a-long-passphrase"}'
# {"token":"eyJ...","user":{"id":"...","username":"admin","role":"admin",...}}

# create a website
curl -s -X POST http://127.0.0.1:3999/api/websites \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $TOKEN" \
  -d '{"name":"My Blog","domain":"blog.example.com"}'
# {"id":"3f2a...","websiteId":"3f2a...","name":"My Blog",...}

The domain field is optional but useful: when set, the tracker can be configured with the domain instead of the id, and the server can reject hits that arrive for a website it does not know.

6. Install the tracker

The server serves the tracker itself at /sumimi.js — it is compiled into the binary, so it is always available whatever you set SUMIMI_APP_URL to. Put this in the <head> of every page you want to measure: 

<script defer
  src="https://your-sumimi-host/sumimi.js"
  data-website-id="3f2a..."></script>

That is the whole integration. A page view is sent automatically on load. There are more ways to install it — self-hosted, on a CDN, for several sites at once — and they are all in the tracker guide.

7. Look at the numbers

Open http://127.0.0.1:3999/ and log in with the admin account. The dashboard is a small HTML shell that loads the frontend JavaScript. By default that frontend comes from a CDN (https://cdn.jsdelivr.net/gh/sumimi-dev/sumimi@main/js), so the backend ships no frontend code; set SUMIMI_APP_URL=/app to serve it from the backend's own js/ directory instead. The tracker at /sumimi.js is always served by the backend itself.

You can also read the same numbers straight from the database file: 

sumimi summary --db /var/lib/sumimi/data.duckdb 3f2a...
sumimi pages --db /var/lib/sumimi/data.duckdb 3f2a... --limit 10

The CLI reference lists every subcommand and every flag.

Just want to look at it first?

You do not need a website to see the dashboard working. sumimi seed fills a database with synthetic demo traffic — invented pages, invented visitors, a plausible traffic shape — so you can evaluate the whole thing without pointing a real site at it: 

# the server must be stopped while the database is written
sumimi seed --db ./demo.duckdb --days 30

# then start it on the demo database
sumimi serve --db ./demo.duckdb --port 3000

Open http://127.0.0.1:3000/ and sign in with the admin account (the first start prints its password once). The seeded website is called "Example Blog". The CLI reference describes the flags.
