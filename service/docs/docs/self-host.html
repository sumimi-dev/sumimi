Self-host on a cheap VPS

A complete deployment of Sumimi on a 1 vCPU / 512 MB machine: a dedicated user, a systemd unit, a real certificate, and backups you can restore from. The server is a single self-contained executable — DuckDB is compiled into it — so deploying it means copying one file onto the box. Nothing here needs more than a few megabytes of RAM. TLS can come from a reverse proxy or from Sumimi itself — the guide covers both.

What the box needs

ResourceAmountNotes
vCPU1Plenty. The server is idle between flushes.
RAM512 MBDuckDB is capped at 256 MB by default so the OOM killer stays away.
Disk10 GBThe database is small; page views are a few dozen bytes each.
OSDebian 12 / Ubuntu 22.04+Any systemd Linux works. Alpine needs libstdc++ and libgcc.
Programsone executablesumimi — the server and the analysis CLI in one program. Self-contained: DuckDB is compiled in.

DuckDB's memory limit is what makes 512 MB viable. Set it explicitly if you want to be sure: 

SUMIMI_DUCKDB_MEMORY_LIMIT=256MB

Other knobs worth knowing about on a small box:

  • SUMIMI_MAX_QUEUE (default 100000) — how many events may be buffered in memory before the oldest are dropped. Under overload the server drops data rather than dying; the counter shows up in /api/heartbeat.
  • SUMIMI_FLUSH_INTERVAL_SECS (default 2) — how often the writer thread commits a batch. Two seconds keeps disk I/O low and means the dashboard lags by at most that.

1. Create the user and the directories

Run the server as its own unprivileged user. It never needs root and it never needs to write anywhere except its data directory. 

sudo useradd --system --home /var/lib/sumimi --shell /usr/sbin/nologin sumimi
sudo mkdir -p /var/lib/sumimi
sudo chown sumimi:sumimi /var/lib/sumimi
sudo chmod 0750 /var/lib/sumimi

2. Install the executable

# download and unpack the release archive
cd /tmp
curl -fsSL https://github.com/sumimi-dev/sumimi/releases/latest/download/sumimi-linux-amd64.tar.gz | tar xz

# install the one executable — that is all there is to do
sudo install -m 0755 sumimi /usr/local/bin/

# the js/ and docs/ directories from the archive (see below)
sudo install -d -m 0755 /opt/sumimi
sudo cp -r js docs /opt/sumimi/

One file, nothing to configure

DuckDB is compiled into the executable, so sumimi is completely self-contained: there is no libduckdb.so to install, no LD_LIBRARY_PATH to set and no ldconfig to run. Copy one file onto the box and it runs.

The archive also ships sumimi-server and sumimi-client as symlinks to sumimi, for people who prefer the explicit names — they are the same file. The unit below uses sumimi serve.

If you would rather keep the program in one directory that is trivially versioned and swapped on upgrades, install it into /opt/sumimi and point the unit's ExecStart at /opt/sumimi/sumimi.

The archive also contains two directories: docs/, which the server serves as this documentation site at /docs, and js/, which holds the dashboard frontend. You only need js/ if you serve the frontend from the backend yourself with SUMIMI_APP_URL=/app — by default the frontend comes from a CDN. The tracker is compiled into the binary, so /sumimi.js works whether or not you copy the directory across.

3. Write the environment file

Secrets do not belong in a unit file or in the repository. Put them in a file only the service user can read. 

sudo install -d -m 0750 /etc/sumimi
sudo tee /etc/sumimi/sumimi.env >/dev/null <<'EOF'
# the instance directory: the events, the accounts, the logs, the secret
SUMIMI_DIR=/var/lib/sumimi
SUMIMI_HOST=127.0.0.1
SUMIMI_PORT=3999

# a long random string; mint one with: openssl rand -hex 32
SUMIMI_JWT_SECRET=replace-me-with-64-hex-characters

SUMIMI_ADMIN_USER=admin
SUMIMI_ADMIN_PASSWORD=replace-me-with-a-long-passphrase

# keep events for a year, then prune
SUMIMI_RETENTION_DAYS=365

# stay inside a 512 MB box
SUMIMI_DUCKDB_MEMORY_LIMIT=256MB
SUMIMI_MAX_QUEUE=100000
SUMIMI_FLUSH_INTERVAL_SECS=2

# directory holding the dashboard frontend and this docs site
SUMIMI_JS_DIR=/opt/sumimi/js
SUMIMI_DOCS_DIR=/opt/sumimi/docs

# the dashboard frontend comes from a CDN by default; uncomment this to
# serve it from the backend's own js/ directory instead (air-gapped installs)
# SUMIMI_APP_URL=/app

# only if Sumimi should manage TLS itself (see section 5, option B)
# SUMIMI_SSL_DOMAIN=example.com
# SUMIMI_SSL_EMAIL=you@example.com
EOF

sudo chown root:sumimi /etc/sumimi/sumimi.env
sudo chmod 0640 /etc/sumimi/sumimi.env

If you leave SUMIMI_JWT_SECRET unset, the server generates a random secret on first run and writes it in the instance directory (/var/lib/sumimi/jwt-secret, mode 0600). That is fine, but setting it explicitly means the secret survives a move to another machine.

4. Write the systemd unit

sudo tee /etc/systemd/system/sumimi.service >/dev/null <<'EOF'
[Unit]
Description=Sumimi web analytics
Documentation=https://sumimi.dev/docs/
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=sumimi
Group=sumimi
EnvironmentFile=/etc/sumimi/sumimi.env
ExecStart=/usr/local/bin/sumimi serve
Restart=on-failure
RestartSec=5

# hardening: the service only ever needs to write its own data directory
NoNewPrivileges=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectSystem=strict
ProtectHome=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes
LockPersonality=yes
ReadWritePaths=/var/lib/sumimi

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now sumimi
sudo systemctl status sumimi

The command line is intentionally empty of flags: everything comes from the environment file, so sudo systemctl edit sumimi is enough to change a setting on a live box.

The unit starts sumimi serve. If you prefer the explicit name, the sumimi-server symlink works just as well. 

sudo journalctl -u sumimi -f

On the very first start the server creates the admin user. If SUMIMI_ADMIN_PASSWORD was not set, the generated password is printed to the log exactly once: 

[sumimi] created the admin user 'admin'
[sumimi] password: 8f3c1b9d0e7a4f26b5c8d1e3a9f7b2c4
[sumimi] store it now — it is not shown again

5. TLS

There are two ways to put this box behind HTTPS, and they are alternatives — pick one. A reverse proxy in front is the traditional setup and works with any proxy you like. Or you can let Sumimi manage the certificate itself, with no proxy at all.

Option A: put a reverse proxy in front

The server binds to 127.0.0.1, so nothing on the internet can reach it directly. A proxy terminates TLS and forwards plain HTTP to port 3999.

Caddy

Caddy obtains and renews a Let's Encrypt certificate on its own — no cron, no certbot. This is the shortest correct configuration. 

sudo tee /etc/caddy/Caddyfile >/dev/null <<'EOF'
analytics.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:3999
}
EOF

sudo systemctl reload caddy

nginx

sudo tee /etc/nginx/sites-available/sumimi >/dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name analytics.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name analytics.example.com;

    ssl_certificate     /etc/letsencrypt/live/analytics.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/analytics.example.com/privkey.pem;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "no-referrer" always;

    location / {
        proxy_pass http://127.0.0.1:3999;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # the tracker is a static file; let it cache briefly
    location = /sumimi.js {
        proxy_pass http://127.0.0.1:3999;
        proxy_set_header Host $host;
        add_header Cache-Control "public, max-age=300";
    }
}
EOF

sudo ln -sf /etc/nginx/sites-available/sumimi /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

With nginx, get the certificate with certbot: 

sudo certbot --nginx -d analytics.example.com

certbot installs a timer that renews the certificate twice a day and reloads nginx.

ACME in general

Either way the certificate comes from Let's Encrypt over ACME, and renewal is automatic. Two things are required for it to work: port 80 must be reachable from the internet, and the domain must already point at your server's IP address. A DNS record that has not propagated yet is the most common reason for a failed first issuance — check with dig +short analytics.example.com.

If port 80 is closed, use the DNS-01 challenge instead (certbot with a DNS plugin, or acme.sh --dns). That works with any DNS provider and needs no inbound port.

Option B: let Sumimi manage TLS itself

If there is no other service on the box that needs port 443, you can skip the reverse proxy entirely. Sumimi can obtain a Let's Encrypt certificate on its own over ACME and renew it in the background — no certbot, no cron job, no proxy just to serve TLS.

Pass the domain and a contact address to the server: 

sumimi serve --ssl example.com --ssl-email you@example.com

In the systemd unit that means adding the flags to ExecStart: 

sudo tee /etc/systemd/system/sumimi.service >/dev/null <<'EOF'
[Unit]
Description=Sumimi web analytics
Documentation=https://sumimi.dev/docs/
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=sumimi
Group=sumimi
EnvironmentFile=/etc/sumimi/sumimi.env
ExecStart=/usr/local/bin/sumimi serve --ssl example.com --ssl-email you@example.com
Restart=on-failure
RestartSec=5

# hardening: the service only ever needs to write its own data directory
NoNewPrivileges=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectSystem=strict
ProtectHome=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes
LockPersonality=yes
ReadWritePaths=/var/lib/sumimi

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl restart sumimi

The same four settings are available as environment variables, so you can keep the unit file free of flags if you prefer:

FlagEnvironment variableDefaultMeaning
--ssl <domain>SUMIMI_SSL_DOMAINnoneThe domain to serve HTTPS for. Without it the server speaks plain HTTP. --ssl-domain is accepted as an alias.
--ssl-email <address>SUMIMI_SSL_EMAILnoneContact address registered with the ACME provider. Let's Encrypt sends expiry notices there.
--ssl-cache-dir <path>SUMIMI_SSL_CACHE_DIR<directory of the database>/acmeDirectory holding the ACME account and the certificates.
--ssl-port <port>SUMIMI_SSL_PORT443The port to listen on for HTTPS.

Where the ACME cache lives by default

By default the cache directory is derived from the database path: it is an acme directory next to the database file. With SUMIMI_DIR=/var/lib/sumimi the cache is /var/lib/sumimi/acme. That is an absolute path, so it does not depend on the working directory of the service, and it lands inside the data directory the hardening above already allows writes to. You do not need to set anything for this to work.

Override it with SUMIMI_SSL_CACHE_DIR if you would rather keep the cache somewhere else: 

# in /etc/sumimi/sumimi.env
SUMIMI_SSL_CACHE_DIR=/var/lib/sumimi/acme

Port 443 has to reach Sumimi directly

The challenge used is TLS-ALPN-01: the ACME server connects to port 443 and negotiates a special certificate over the TLS handshake itself. That means nothing may sit in front of Sumimi on port 443 — no proxy, no load balancer, no port-forward to another machine. If a reverse proxy terminates TLS in front of the server, use the proxy's own ACME support instead (Caddy, or nginx with certbot) and leave --ssl unset.

Port 80 does not need to be open: the certificate is validated over port 443 alone. The domain's DNS record must already point at this server's IP address, or the first issuance will fail.

Back up the ACME cache

/var/lib/sumimi/acme — the acme directory next to the database, or whatever you set SUMIMI_SSL_CACHE_DIR to — holds the ACME account and the issued certificates. It is small, but lose it and the server has to register a new ACME account and re-issue the certificate — and Let's Encrypt rate-limits repeated issuance for the same domain. Add it to the backup script next to the database.

6. Firewall

Only the proxy needs to be reachable. Everything else stays closed. 

sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status

Port 3999 is deliberately not opened: the server is bound to loopback and is only reachable through the proxy.

If you took Option B and let Sumimi manage TLS itself, port 443 has to reach the Sumimi process directly, so bind the server to a public address and open the port: 

# in /etc/sumimi/sumimi.env
SUMIMI_HOST=0.0.0.0

# and open it
sudo ufw allow 443/tcp

Port 80 stays closed — the ACME challenge runs over port 443.

7. Backups

An instance is a directory, so a backup is one directory copy. It holds the events (data.duckdb), the accounts, the log and the cache (instance.sqlite), the signing secret (jwt-secret), the logs and the TLS cache. Stop the service first so the copy is consistent — DuckDB's write-ahead log means a live copy can otherwise be incomplete. There is no library to back up: the executables are self-contained, so only the instance directory needs copying. 

# a nightly snapshot
sudo tee /usr/local/bin/sumimi-backup >/dev/null <<'EOF'
#!/bin/sh
set -eu
DEST=/var/backups/sumimi
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$DEST"
systemctl stop sumimi
# the events, the accounts and the signing secret
cp -a /var/lib/sumimi/data.duckdb "$DEST/data-$STAMP.duckdb"
cp -a /var/lib/sumimi/instance.sqlite "$DEST/instance-$STAMP.sqlite"
# the write-ahead log, if the server was killed instead of stopped —
# it holds whatever was written since the last checkpoint
cp -a /var/lib/sumimi/instance.sqlite-wal "$DEST/" 2>/dev/null || true
cp -a /var/lib/sumimi/jwt-secret "$DEST/" 2>/dev/null || true
# the ACME account and certificates, if Sumimi manages TLS itself
cp -a /var/lib/sumimi/acme "$DEST/" 2>/dev/null || true
systemctl start sumimi
find "$DEST" -name 'data-*.duckdb' -mtime +30 -delete
EOF
sudo chmod 0755 /usr/local/bin/sumimi-backup
sudo tee /etc/cron.d/sumimi-backup >/dev/null <<'EOF'
30 3 * * * root /usr/local/bin/sumimi-backup
EOF
sudo chmod 0644 /etc/cron.d/sumimi-backup

Keep the copies off the box as well — rsync to another machine, or restic to object storage you control. A backup that lives on the same disk is not a backup.

Restoring

sudo systemctl stop sumimi
sudo cp -a /var/backups/sumimi/data-20260115T033000Z.duckdb /var/lib/sumimi/data.duckdb
sudo cp -a /var/backups/sumimi/instance-20260115T033000Z.sqlite /var/lib/sumimi/instance.sqlite
sudo chown sumimi:sumimi /var/lib/sumimi/data.duckdb /var/lib/sumimi/instance.sqlite
sudo systemctl start sumimi
curl -s http://127.0.0.1:3999/api/heartbeat

8. Retention

Set SUMIMI_RETENTION_DAYS to a number of days and prune regularly. The retention window is a first-class setting: it is stored per website, returned by GET /api/websites/:id, and honoured by the CLI. 

# stop the service, then prune the database in place
sudo systemctl stop sumimi
sumimi prune --dir /var/lib/sumimi 3f2a...
sudo systemctl start sumimi

Schedule it in the same cron file as the backup. Pruning before the backup keeps the backup small. The service has to be stopped while it runs — DuckDB allows only one writer per file.

9. Upgrades

sudo systemctl stop sumimi
sudo install -m 0755 sumimi /usr/local/bin/
sudo systemctl start sumimi
sudo journalctl -u sumimi -n 20

Schema changes are additive and need no migration step, so upgrading in place is safe. Take a backup first anyway.

The dashboard frontend and the tracker

Two different JavaScript files are involved, and they are served in two different ways:

FileWhat it isServed by
sumimi.js The tracker you put on your own website. It sends the page views. The backend itself, at /sumimi.js. It is compiled into the binary, so it is always available — no CDN, no configuration.
sumimi-app.js
sumimi.css		 The dashboard frontend — the pages you log into to read your statistics. A CDN by default. The backend serves only a tiny HTML shell at / that points at <base>/sumimi-app.js.

Serving the dashboard frontend from a CDN

This is the default and you do not have to configure anything. The backend serves a deliberately tiny HTML shell at / that references sumimi-app.js and sumimi.css under a base URL — and that base URL defaults to: 

SUMIMI_APP_URL=https://cdn.jsdelivr.net/gh/sumimi-dev/sumimi@main/js

jsDelivr serves this public GitHub repository directly, so the dashboard frontend is fetched from https://cdn.jsdelivr.net/gh/sumimi-dev/sumimi@main/js/sumimi-app.js and .../sumimi.css. Two consequences: the backend ships no frontend code at all, and the dashboard picks up frontend fixes without you upgrading the server.

You can point SUMIMI_APP_URL at any other base URL — your own CDN, a self-hosted copy: 

SUMIMI_APP_URL=https://cdn.example.com/sumimi-app

The shell then references https://cdn.example.com/sumimi-app/sumimi-app.js and .../sumimi.css instead.

Serving the dashboard frontend from the backend

On an air-gapped machine there is no CDN to fetch from. Set SUMIMI_APP_URL=/app and the backend serves the two frontend files from its own js/ directory instead: 

# in /etc/sumimi/sumimi.env
SUMIMI_APP_URL=/app
SUMIMI_JS_DIR=/opt/sumimi/js

The shell then references /app/sumimi-app.js and /app/sumimi.css, and the backend reads them from disk at request time — so you can update the frontend by replacing the files in js/, without restarting the server. The files are also served directly at /app/sumimi-app.js and /app/sumimi.css either way, so that fallback path always works.

Whatever you set here, the tracker is unaffected: sumimi.js is always served by the backend itself, because your own website has to be able to reach it.

A note on Cloudflare

You do not need Cloudflare, and Sumimi is designed to work without it. If you happen to put your site behind Cloudflare, the proxy can supply a country code header, which is the only way Sumimi learns anything about geography: 

SUMIMI_COUNTRY_HEADER=CF-IPCountry

Without such a header, no geographic information is recorded at all — not even a country. See the privacy page.

Checklist

  • Executables installed on the PATH; DuckDB is compiled in, so there is no shared library to install and no loader configuration to do.
  • Dashboard frontend reachable: from the CDN (the default), or from the backend with SUMIMI_APP_URL=/app if the box has no outbound network access.
  • Environment file at /etc/sumimi/sumimi.env, mode 0640.
  • Data directory owned by the sumimi user, mode 0750.
  • systemd unit enabled and restarting on failure.
  • Proxy in front on 443, server bound to loopback only.
  • Certificate issued and auto-renewing (check the renewal log).
  • Backup running, and you have tested a restore.
  • If Sumimi manages TLS itself: port 443 reaches the Sumimi process directly, and the ACME cache directory is included in the backups.
  • Retention window set, prune scheduled.
