# 会话 id 的「邻近优化」（时间桶 + 哈希）—— 2026-11-27 凌晨

**问题**：会话 id 现在是纯哈希（`SHA-256(addr‖ua‖site)`）。如果让它带上邻近结构
（8 字节 = 2 字节小时桶 + 6 字节哈希），能不能省盘？

**答**：不能。最好的那一档与纯哈希一模一样，小时桶反而更贵。

## 跑法

```bash
cargo build --release --example identity_scale
./target/release/examples/identity_scale \
  --rows 1000000 --visitors 100000 --events-per-visit 4 --interleave 4 \
  --days 30 --threads 4 --memory-limit 256MB --no-parquet --repeats 7 \
  --layouts blob8_bvisit,bucket8_bvisit,bucket8day_bvisit,bucket8const_bvisit
```

工具里新加的三个 layout（`service/examples/identity_scale.rs`）：

| layout | 会话 id |
|---|---|
| `bucket8` | 2 字节**小时桶**（行的时间）+ 6 字节访客哈希 |
| `bucket8day` | 2 字节**天桶** + 6 字节访客哈希 |
| `bucket8const` | 2 字节**恒定前缀** + 6 字节访客哈希（桶能有的最好一档：不分裂任何人） |

## 数（100 万行 / 10 万访客 / 30 天 / E=4 / 交错 4 / 256 MB / 4 线程）

| 形状 | 整行 B/行 | 会话列 B/行 | 窗口内不同 id 数 |
|---|---|---|---|
| `blob6_bvisit` | 16.27 | 3.15 | 80,001 |
| `blob8_bvisit`（D-061 拍的） | 16.53 | 3.41 | 80,001 |
| `blob12_bvisit` | 17.31 | 4.19 | 80,001 |
| `bucket8_bvisit`（小时桶） | 16.79 | 3.67 | 202,305 |
| `bucket8day_bvisit`（天桶） | 16.53 | 3.41 | 200,043 |
| `bucket8const_bvisit`（桶恒定） | 16.53 | 3.41 | 80,001 |

**读法**：字典压下，一个段里每个不同的值存一次，每行另有一个索引 ⇒ 这一列的每行
成本只有「索引位宽」与「条目字节 ÷ 重复次数」两项 ⇒ **熵本身不额外付钱，宽度要付钱**
⇒ id 的形状能动的只有宽度（8→6 = 0.26 B/行），而桶让宽度不变、重复次数变少
（不同 id 数 80,001 → 202,305 ⇒ 摊销变差）⇒ 反而贵 0.26 B/行。

`visitors_*.txt` 是同一形状、不同访客数的一档：**不同 id 数从 8,001 到 80,001 会涨
（2.10 → 3.41 B/行），从 80,001 到 200,001 就不动了**（字典按段算，位宽是阶梯的）。

## 两条前提

1. **每一档一个进程**（cpu 不可在一轮里互比，顺序效应 20%–30%）；盘上的字节数是准的。
2. **模型里访客摊在整整 30 天上**，不是真实站那种几分钟一簇 ⇒ 小时桶那一行是模型的最坏
   情形；但最好的一行（持平）也说明桶没有便宜可占。
